# Deployment and upgrades

Current approval policy: single confirmation by default; independent approval
requires `ADMIN_INDEPENDENT_APPROVAL_ENABLED=true`. Existing records keep their
original policy. See [schema v6 migration and API behavior](approval.md). References
to separate approval below describe the enabled mode.

## Secrets and identity

`cmd/init-local` creates fresh values in an ignored directory with restrictive
permissions. It refuses to overwrite an existing directory. Never commit runtime
files or copy them into a Docker build context. All production credentials must
be generated by the deployer, separately for each installation.

Required API file settings: `ADMIN_MYSQL_DSN_FILE`, `ADMIN_JWT_SECRET_FILE`,
`ADMIN_BOOTSTRAP_TOKEN_FILE`, `ADMIN_SIGNING_KEY_FILE`. Secret files must be regular
files with permissions at most `0600`. The signing file is base64 Ed25519 private
key material; `signing.pub` contains only the base64 public key.

Optional settings: `ADMIN_LISTEN_ADDRESS`, `ADMIN_WEB_ROOT`,
`ADMIN_TRUSTED_PROXY_CIDRS`, `ADMIN_GITHUB_CONFIG`. SMTP uses
`ADMIN_SMTP_ADDRESS`, `ADMIN_SMTP_USERNAME`, `ADMIN_SMTP_FROM` and
`ADMIN_SMTP_PASSWORD_FILE`. SMTP requires STARTTLS; credentials/errors are never
returned to the browser. `ADMIN_EMAIL_CONFIRMATION_ENABLED=false` explicitly
skips email confirmation but not authorization, CSRF, task approval or signatures.

For production, terminate HTTPS at your ingress, keep `ADMIN_COOKIE_SECURE=true`,
restrict the API listener to the trusted network, and configure exact proxy CIDRs.
Do not reuse the local Compose example's subnet or insecure-cookie setting as
production defaults. Restrict access to MySQL and use a dedicated management user.

## Agent inventory

```json
{
  "host_id": "host-a",
  "api_url": "https://admin.example.com",
  "token_file": "/etc/skygo-admin/private/token",
  "public_key_file": "/etc/skygo-admin/signing.pub",
  "state_dir": "/var/lib/skygo-admin/agent",
  "services": [{
    "id": "node-a",
    "compose_file": "/srv/example/compose.yaml",
    "env_file": "/srv/example/runtime.env",
    "project": "example",
    "compose_service": "node-a",
    "image_variable": "NODE_A_IMAGE",
    "allowed_images": ["example/node"],
    "health_url": "http://127.0.0.1:19081/healthz",
    "config_path": "/srv/example/config/node-a.json",
    "skygo_registry": true,
    "allow_logs": false
  }]
}
```

Compose must use the named image variable, and each managed service must have one
container. The agent uses `up -d --no-deps --pull never` after pulling the approved
immutable digest. It cannot execute remote shell input. Registry login is local
Docker configuration; registry credentials are not stored in management tasks.

Persist the agent state directory and retain it during upgrades. Access to Docker
is equivalent to host administration: run the agent only on intended managed hosts.
Mount configuration **directories**, not individual files, when using atomic file
replacement. A published configuration is written and the service restarted;
health determines whether activation is confirmed.

Logs are disabled per service by default. When enabled, only the latest 100 lines
(up to 16 KiB) are returned, with common credential-bearing lines redacted. The
workload must also redact its own logs; generic filtering cannot identify all
application secrets. Configure tasks never carry secrets.

## Optional GitHub workflow

A local JSON file selected by `ADMIN_GITHUB_CONFIG` contains `repository`,
`workflow`, `allowed_refs` and an absolute `token_file` path. The token file must
be private. `build.yml` accepts only the three public components and two Linux
architectures. It builds archives by default. Explicit `publish_images: true` configuration
enables digest-pinned GHCR publication and a separately signed image manifest;
see [release workflow](releases.md). Dispatch network failures remain uncertain and are not automatically
retried. Inspect the workflow runs before dispatching again.

## Upgrades and recovery

Back up MySQL and the agent state before upgrades. Keep JWT and signing keys,
node credentials and persistent volumes. Apply a required schema migration
explicitly with a suitably privileged account, then replace the component images.
Ordinary startup and image changes do not run migrations or initialization.

Mark management API/Web service definitions `control_plane: true`. Their tasks
are blocked while another task is queued, dispatched or uncertain. The agent
continues running independently and delivers its receipt after API recovery.
Do not replace the agent process while it executes a task; stop it gracefully
and preserve its journal before restarting the new binary.

A failed task releases its service lock. An uncertain task retains the lock while
the agent probes for evidence. Investigate the actual container and configuration
before local operator resolution; never delete a receipt and resubmit the old
command. The source-level journal format is versioned with the command contract.

After inspecting an uncertain operation, a host administrator can explicitly close
it as failed, without running anything again:

```sh
# Stop the managed ops-agent process first using its normal service manager.
ops-agent -config /absolute/path/to/agent.json -resolve-failed TASK_ID
# Restart ops-agent normally; it delivers the failed receipt to the controller.
```

This action refuses while the agent holds its state lock or when the receipt is
not uncertain. The result is audited as `OPERATOR_RESOLVED_FAILED`. A new task
requires fresh approval. This is an operator assertion of failure, not automated
verification or successful rollback.
